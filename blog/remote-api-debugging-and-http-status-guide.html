一、责任边界划分：4xx 客户端错误 vs 5xx 服务端错误

在 HTTP 协议（RFC 9110）中，状态码首位数字严格定义了问题归属：

  • 4xx（Client Error）：请求本身有问题（参数错误、凭据无效、未授权）；
  • 5xx（Server Error）：服务端处理出现异常（程序崩溃、网络超时、上游宕机）。

搞清楚状态码的确切定义，能在联调沟通中节约 80% 的扯皮时间。

二、高频报错深度剖析与排查秘籍

1. 401 Unauthorized vs 403 Forbidden：谁的责任？

这两个状态码经常被前后端开发混淆，但它们的协议语义有着本质分野：

状态码协议核心定义典型业务场景排查要点
401 Unauthorized未认证（缺少有效身份证明）请求头缺少 Authorization、JWT 令牌已过期、Token 签名无效检查前端是否正常携带凭证；Token 是否因时钟偏差判定已过期
403 Forbidden已认证，但无访问权限（禁止访问）普通用户试图调用管理员接口、IP 被白名单防火墙拦截身份是合法的，但角色（RBAC）不足；或触发了 WAF 防火墙风控

💡 黄金记忆法则：
• 收到 401：是“你是谁？”的问题 —— 引导用户去重新登录或刷新 Token；
• 收到 403：是“凭什么？”的问题 —— 已经知道你是谁，但当前业务规则不允许你碰这个资源。

2. 502 Bad Gateway vs 504 Gateway Timeout：反向代理的两种绝望

现代微服务架构中，前端请求通常首先到达反向代理层（Nginx / Ingress / 负载均衡 SLB），再转发到后端 Spring Boot、Go 或 Node.js 业务容器。

[前端浏览器] ---> (HTTP 请求) ---> [Nginx 网关] ---> [Upstream 后端业务容器]

当 Nginx 与后端通信出问题时，便会产生以下两种典型报错：

① 502 Bad Gateway（错误网关）

  • 底层原理：Nginx 尝试连接后端服务时，后端直接返回了非法响应，或者连接被瞬间拒绝/重置（Connection Refused / Reset）；
  • 常见根因：
    1. 后端业务进程遭遇 OOM（内存溢出）被系统杀掉，服务根本没在监听端口；
    2. 部署发版中，旧 Pod 已销毁而新 Pod 尚未就绪，服务注册中心未及时下线；
    3. 后端服务返回了非标准的 HTTP 协议头。

② 504 Gateway Timeout（网关超时）

  • 底层原理：Nginx 成功与后端建立了连接，但在配置的等待时间内（如 proxy_read_timeout 60s），后端迟迟没有吐出任何数据；
  • 常见根因：
    1. 数据库遭遇死锁或慢查询，单个大 SQL 阻塞长达几十秒；
    2. 后端同步调用了第三方接口，第三方服务卡死导致线程池被耗尽。

三、排障盲区：URL Query 参数的三大经典“暗坑”

除了状态码，许多接口请求在传参阶段就已因特殊字符转义不当而暴毙：

1. 经典暗坑一：加号 + 变成空格的悲剧

在 URL 的 Query 参数中，标准规定加号 + 会被服务端自动解码为空格（ ）。

如果接口传递 Base64 编码字符串或手机区号（如 +86），若未经过 encodeURIComponent 转义，后端拿到的就会变成 86 或包含空格的非法 Base64，导致验签失败直接报 400。

正确做法：将 + 转义为 %2B。

2. 经典暗坑二：参数截断幽灵（& 与 #）

如果传递的参数值本身包含 &（如密码 pass&word）或 #（锚点），浏览器会将其误认为是下一个 Query 字段的分隔符或网页哈希锚点，导致整个 URL 被腰斩，后端收到的字段严重残缺。

3. 经典暗坑三：复杂数组参数格式不一致

不同后端框架对数组参数解析的默认预期各不相同：

  • 逗号分隔型：?ids=1,2,3
  • 中括号重复型（PHP/Spring 常见）：?ids[]=1&ids[]=2
  • 重复字段型（FastAPI/Go 常见）：?ids=1&ids=2
